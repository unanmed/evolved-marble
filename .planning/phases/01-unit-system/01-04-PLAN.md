<objective>
Implement `class Unit implements IUnit` — the single derived-value accessor and the level/experience/upgrade state machine — plus its two test files.

This plan delivers UNIT-01 (the full attribute set readable through one accessor) and UNIT-06 (experience accrual, level-up, per-class growth, health restore, equipment/skill unlock). It implements the contract approved in plan 01-02 and consumes the tables from plan 01-03.

Purpose: `Unit` is the core object every later system reads (physics, control, render) — all of them go through `getAttribute(kind)`.
Output: `src/units/Unit.ts`, `tests/units/attributes.test.ts`, `tests/units/leveling.test.ts`.

Design choices carried from the resolved research (OQ-2/OQ-3/OQ-4/OQ-7; surfaced at the plan-01-02 review gate):
- Base values are the class's level-1 values. **Attack growth is level-scaling (OQ-2):** the per-level increment scales with the current level, so `Attack(L) = attackBase + attackGrowth·L·(L−1)/2` (the level-1 value is exactly `attackBase`). **Index basis (stated explicitly, for the 01-02 review gate):** a level-up *out of* level L — i.e. the level being LEFT — adds `attackGrowth × L`, and the destination level contributes NOTHING to its own increment; equivalently the cumulative value at the current level L is `attackGrowth·L·(L−1)/2`. Swordsman level 3 = `60 + 10·3·2/2 = 90` (level 1→2 adds 10, level 2→3 adds 20). **Defense growth is flat (OQ-2):** `Defense(L) = defenseBase + defenseGrowth·(L−1)` — a constant per level, NOT a `k·L` curve, because 防御 is a percentage damage-reduction stat.
- Control level grows +5 per level (`CONTROL_LEVEL_GROWTH_PER_LEVEL`).
- `maxHpGrowth` is a per-class value from `CLASS_DEFS` (not stated in the spec; OQ-3, marked for calibration); on level-up `hp += maxHpGrowth`, capped at the current 生命上限.
- On level-up the threshold is subtracted and the surplus carried, and the check repeats so one xp gain can trigger multiple level-ups (OQ-4).
- Classes with no skill listed in the spec get an empty learned-skill list (OQ-7).
- **Spawn at full health:** the constructor initializes `#hp` from the level-1 `MaxHealth` **actually returned by `getAttribute(AttributeKind.MaxHealth)`** — i.e. the rolled `#maxHpBase` at level 1, plus any injected modifier contribution — NOT the class `#def.maxHp`. Using the class base leaves `Health < MaxHealth` whenever the roll differs from the base, so the level-1 read is the authoritative spawn value.
- **Rolled bases, not class constants:** every level-grown read starts from the ROLLED spawn value — `MaxHealth` from `#maxHpBase`, `ControlLevel` from `#controlLevelBase`, `Attack` from `#attackBase`, `Defense` from `#defenseBase` — never from `#def.maxHp`/`#def.attack`/`#def.defense`. The class def supplies only the growth coefficients (`attackGrowth`/`defenseGrowth`/`maxHpGrowth`), the control-level per-level increment constant, and the ratios; the 7 rolled values come from `ISpawnAttributes`. This is what makes 01-05's normal-distributed spawn observable through `getAttribute` (a constant `#def.attack` would give σ=0 and break 01-05 Test 4).
- **Modifier injection:** the constructor takes an optional third argument (`modifiers: readonly IModifier[]`, default `[]`) so the 加成 path (`#applyModifiers`, `getModifiers()`) is exercised against a non-empty list. Phase 1 ships no bonus values of its own, so this injection is the only way to observe a non-empty modifier contribution; `IUnit` gains no mutator — the locked interface is unchanged.
- **Modifier scope (Phase 1):** `#applyModifiers` is wired into exactly the three combat stats — `MaxHealth`, `Attack`, `Defense`. `IModifier.kind` is typed as `AttributeKind` (locked contract, unchanged), so `getModifiers()` will faithfully return a modifier for any kind; a modifier targeting any OTHER kind is therefore returned but intentionally not applied yet. This is a deliberate, documented scope boundary, not an inconsistency: Phase 1 has no bonus source that emits a non-combat-kind modifier, and later phases that introduce one (e.g. a 移动速度 or 控制等级 buff) extend the same `#applyModifiers` call sites rather than reshaping `IModifier`. Do NOT silently broaden the switch to route every `AttributeKind` through `#applyModifiers` in this phase — that would require inventing scaling semantics for `WeaponRatio`/`Mass`/`ExperienceRatio` that no source artifact defines.
- `takeDamage` exists only so the level-up health-restore is observable; damage computation itself belongs to Phase 2.
</objective>
